# Задание 4. Проектирование продажи ОСАГО

## Проектирование osago-aggregator

### Требования к хранилищу данных
Для osago-aggregator необходимо собственное хранилище данных, однако объем хранимой информации будет относительно небольшим. В базе данных потребуется сохранять следующие ключевые данные:

- **Идентификатор заявки** (внутренний, полученный от core-app)
- **Текущий статус обработки заявки** (в работе, завершена, ошибка)
- **Идентификаторы заявок** в системах страховых компаний (полученные при создании заявки у каждого партнера)
- **Временные метки** создания и обновления для контроля таймаутов и ведения логов

### API для взаимодействия с core-app
Учитывая установленное бизнес-требование о 60-секундном таймауте, API между сервисами должно быть реализовано в асинхронном формате. Это позволит избежать блокирующих операций и обеспечит эффективную обработку запросов в условиях высоких нагрузок.

### Выбор средства интеграции
Бизнес-требование о немедленном отображении предложений по мере их поступления диктует необходимость использования асинхронных уведомлений о результатах обработки.

Рекомендуется комбинированный подход:
- **REST API** для инициирования процесса обработки заявки
- **Message Broker** для асинхронной передачи результатов и уведомлений

## Проектирование API для веб-приложения

### Функциональные требования
Веб-приложению требуется API для выполнения следующих операций:
- Передача данных для формирования заявки на ОСАГО
- Получение предложений от страховых компаний в режиме, приближенном к реальному времени

### Выбор технологии интеграции
Для взаимодействия между веб-приложением и core-app оптимальным решением является использование **REST API** с механизмом периодического опроса.

Этот выбор обусловлен несколькими ключевыми факторами:
- **Простота реализации** и сопровождения по сравнению с WebSocket
- **Отсутствие необходимости** в поддержании постоянных соединений
- **Надежность** работы через стандартные HTTP-протоколы
- **Упрощенная балансировка** нагрузки между экземплярами сервиса

### Схема взаимодействия
1. Веб-приложение отправляет REST-запрос для создания заявки на ОСАГО
2. После успешного создания заявки веб-приложение начинает периодически опрашивать core-app через REST API на предмет появления новых предложений
3. Сервис core-app выступает в роли подписчика топика `osago-quotes-ready` в Message Broker
4. При получении нового предложения от osago-aggregator через Message Broker, core-app сохраняет его в своем хранилище
5. При последующих запросах от веб-приложения core-app возвращает накопленные предложения

## Паттерны отказоустойчивости

### Взаимодействие osago-aggregator ↔ Страховые компании

| Паттерн | Область применения | Обоснование |
|---------|-------------------|-------------|
| **Timeout** | Все запросы к внешним страховым компаниям | Бизнес-требование о 60-секундном максимальном времени ожидания требует реализации таймаутов на стороне агрегатора для предотвращения блокировки ресурсов |
| **Retry** | Запросы к внешним страховым компаниям | Обеспечивает обработку временной недоступности партнерских систем |
| **Rate Limiting** | Не применяется на данном участке | Ограничение частоты запросов обычно настраивается на стороне провайдера услуг. Может потребоваться только в случае установления ограничений со стороны страховых компаний |

### Взаимодействие core-app ↔ osago-aggregator

| Паттерн | Область применения | Обоснование |
|---------|-------------------|-------------|
| **Timeout** | POST-запросы инициирования заявок | Защищает core-app от блокировки при отсутствии ответа от osago-aggregator |
| **Retry** | POST-запросы инициирования заявок | Обеспечивает обработку временной недоступности сервиса агрегации |
| **Rate Limiting** | Входящие запросы от веб-приложения к API core-app | Защита системы от пиковой нагрузки в 2500 одновременных пользователей и предотвращение DoS-атак путем ограничения количества запросов с одного пользователя/IP-адреса |

## Учет распределенной архитектуры

### Хранилище osago-aggregator
Хранилище данных должно быть общедоступным и обеспечивать согласованный доступ для всех экземпляров агрегатора. Это гарантирует, что любой инстанс сервиса сможет получить и обновить состояние заявки независимо от того, какой именно экземпляр инициировал ее обработку.

### Балансировка нагрузки
Использование REST API позволяет применять стандартные методы балансировки нагрузки без необходимости реализации сложных механизмов маршрутизации, таких как Sticky Sessions, что упрощает архитектуру и повышает надежность системы.
